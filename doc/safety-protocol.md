## 1. 上游拦截的现实

两家 Provider 的行为不对称，结论是：**上游不能作为合规兜底**。

| Provider | 输入侧拦截 | 流式中拦截 | 可观测信号 |
|---|---|---|---|
| DeepSeek | 无专门错误码 | 无专门错误码 | 只能靠响应形态推断（空 content / `finish_reason` 异常 / 拒绝性文本） |
| 智谱 | 有错误码 | **只返回理由，不返回错误码** | 同上 |

因此不采用「有错误码才处理」的策略，改为**响应形态信号 → 统一 `error.code`**。

## 2. 错误码扩展

现有 `error.code`：`no_model` / `invalid_model` / `unconfigured` / `no_content` / `provider_error` / `parse_error`。

新增：

| code | 语义 | 可重试 | UI 动作 |
|---|---|---|---|
| `content_blocked` | 上游安全策略拒绝（输入或生成中） | **否** | 展示拦截说明，不展示已流出的片段，提供重新表述入口 |
| `no_content` | 提取/组装未得到可用内容（**保留原语义**） | 是 | 提示检查输入后重发 |

**`content_blocked` 必须独立于 `no_content`**：前者重试只会被再拦一次并浪费额度，后者重试有意义。

## 3. 判定路径（两条都要覆盖）

1. **`finish_reason` 路径**：出现异常终止值即判拦截；
2. **内容路径**：流中收到拒绝性文本（含道歉、免责、无法协助等模式）即判拦截。

只赌一条会漏。两条任一命中即触发。

### 3.1 拦截后必须回滚本轮历史

**这一条是硬要求**：一旦判定拦截，已流入前端的部分内容**不得进入下一轮的 `messages`**。

否则下一轮会把被拒内容原样回传上游，轻则再次被拦，重则触发用户级冷却。

实现要点：`runToolLoop` 需要在流中断时丢弃本轮追加的 assistant 消息，而不是照常 `appendResults` 或保留半截内容。

## 4. 输入侧本地前置过滤

上游不兜底 ⇒ 本地必须有一层。

| 层 | 内容 | 位置 |
|---|---|---|
| 词表匹配 | 涉政/涉黄/暴力的高风险词表 | 客户端优先（数据不出端） |
| 结构规则 | 超长、纯乱码、重复刷屏 | 客户端 |
| 语义判定 | 隐含违规 | 不单独做，交给上游 + 形态归一 |

命中后不进入诊断流程，直接返回固定话术（见 §5 的硬拦截）。

> 词表不随仓库分发具体内容，只放规则骨架；实际维护建议走配置。

## 5. 三级处置

三类输入不能用同一套话术，必须分开：

### 5.1 硬拦截（违规内容）

- 范围：涉政、涉黄、暴力等明确违规。
- 行为：固定话术 + **禁用全部工具** + 不进诊断流程。
- 要求：不解释判定依据，不与被拒内容继续对话。

### 5.2 软引导（与业务无关）

- 范围：无厘头提问、要求干活但无方向、方向明确但与本产品无关。
- 行为：**第一次**引导回业务（一句话 + 能力清单）；**第二次**仍无效则给简短说明后结束，不纠缠、不反复劝说。
- 禁止：连续追问「你想诊断哪道题？」这类强迫式引导。

### 5.3 关怀转介（声称心理问题）

- 行为：**不做诊断式追问**，不推测原因，不提供心理建议。
- 输出：表达关切 + 给专业求助渠道 + 一句「我可以帮你处理学习上的问题」后结束。
- 风险提示：这一条最容易被写成「热情追问」，是本协议里**风险最高的一类**，实现时必须锁定行为——不追问。

## 6. 设备标识（`user` 字段）

### 6.1 为什么要做

智谱的内容安全策略可能依据用户标识对该用户暂停服务，因此请求需要携带稳定的终端用户标识。

### 6.2 规范

| 项 | 规定 |
|---|---|
| 字段位置 | **请求体 `user` 字段**（OpenAI 兼容规范中的终端用户标识），不是 HTTP header |
| 值 | 纯随机 UUID，**绝不含设备名、主机名、用户名或任何可识别信息**（该值会送到上游厂商侧） |
| 稳定性 | 同设备多次请求保持一致，否则上游无法关联滥用记录，字段失去意义 |
| 可重置 | 设置页提供「重置设备标识」入口（合规要求：可撤销） |
| 与日志标识的关系 | 现有 `X-Client-Id` 是请求追踪用，与 `user` 是两件事，不要混用 |

### 6.3 已知影响

- 该标识一旦被上游标记，可能影响该设备的可用性；因此**演示与测试前应能重置**，避免演示中途被拦。
- 部分自定义 OpenAI 兼容端点可能对未知字段做严格校验，需要开关控制是否携带。

## 7. 图片上传明示

| 模式 | 数据处理 | 必须提示 |
|---|---|---|
| 本地识别（OCR → 文字） | 图片不出端 | 「图片将在本地转成文字后发送」 |
| 多模态识别（图片直传） | **图片会上传至模型服务商** | 「此模式会把图片发送至模型服务商」 |

纯文本模型下只剩第一种，界面上不应表现为存在选择。

> 术语注意：本系统**没有独立的云端 OCR 服务**。只有「本地识别」与「多模态识别」两条路径，文档与界面均不得写「云端 OCR」。

## 8. 本地数据与合规

- 无账号、无数据库：题目与诊断结果存浏览器本地（localStorage / IndexedDB）。
- 必须提供「清除全部本地数据」入口（已实装）。
- 不自动上传本地数据；任何外发必须先获同意（见 §7）。
- 涉及未成年人数据，需在服务协议中明示数据处理范围。
